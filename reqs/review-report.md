## 1. 一句话结论

草案是一份**带实现设想的“功能愿望清单”**，不是可开发、可验收的 SRS：核心实体「组件」的标识规则自相矛盾，状态/颜色/进程数/表数在 docx 与 drawio 之间各说一套，全文没有一条可执行验收条件，而 drawio 目前只描述了“只读监控”，**工具最核心的“组件级批量操作”在执行图里完全不存在**。可取的是三个方向性判断（组件视角聚合四仓 / 远程+本地双数据源兜底 / 看板式状态可视化），其余需重写。

**审核评级**

| 维度 | 结论 |
|---|---|
| 需求完整性 | 不通过：HLR 承诺的版本/基线/CI 管理在 LLR 无设计；“前端交互全覆盖”实际只有 1 页 |
| 内部一致性 | 不通过：组件标识、状态枚举、颜色、进程数、表数 5 处硬冲突 |
| 可测试性/可验收性 | 不通过：0 条 AC；“炫酷/丝滑/实时/秒级/高并发/性能极高”均为不可测措辞 |
| 可执行性（drawio） | 不通过：见第 4 节，不能作为执行依据 |
| 数据与安全 | 不通过：3 张表无主外键；token 明文 json；破坏性操作无保护 |
| 方向与价值 | 通过：组件级聚合 + 批量操作 + 双源兜底是成立的 |

**问题规模**：6 路评审合计 **167 条发现**（前 5 路 137 条：P0 42 / P1 54 / P2 41；红队复审 30 条）。需求文档若要进入开发，P0 必须全部在 v0.2 冻结前关闭。

## 3. 其余关键问题（按域）

- **需求质量**：两份文档不是同一需求集（drawio 独有 SYNC/CREATE/FETCH/文件树/提交历史，docx 独有批量操作）；“四大核心能力”只列 3 项；“一个组件=四仓不可改动”与 drawio“通常四个”矛盾；无角色/权限/离线/升级/日志/诊断/磁盘/单实例需求；无需求 ID 与变更记录。
- **Git 语义**：比较基准（哪条分支）未定义，单值 `latest_commit` 放不下 per-branch head → 本地 feature 分支对远程 main 会全量假 CONFLICT；dirty 不参与聚合也不阻断；`NO_UPSTREAM` 三子型未区分；空仓库/unborn、shallow、detached、tag 移动/删除未建模；Tag 一致性（基线）无状态；`unpush_commit_count` 在无 upstream 时不可信；外部 git 并发/`.git/index.lock`、LFS、MAX_PATH、大小写、网络盘全无覆盖。
- **架构/可行性**（评审 03，P0×9）：进程数量/归属两套事实源且无监督者与 IPC；“多进程同写嵌入式库”不可行（候选库均不支持多进程并行写，SQLite 仅多读+单写）；“高性能嵌入式数据库（优于 SQLite）”是伪需求——本场景数据量 <50MB，瓶颈在 git IO/网络而非 DB；4,000 仓按草案字段逐项取需 **8,000–48,000 次请求**，“120s 超时”只在最乐观路径成立；400 仓 / 30s 本地全量扫描要求每仓 ≤75ms，而 Windows 上 MBD 大仓 `git status` 实测 150ms–2s，**超预算 2–25 倍**；CI 400 仓 × 2 次/分 = **48,000 请求/小时**；首启无门控（表 1 未就绪时本地目录全判“否”且无重判回路）；无单实例/迁移/崩溃转储/安装升级/WebView2 Runtime 分发；token 明文 json、无 TLS/代理/日志脱敏/审计。
  - **推荐并已并入 SRS 第 12 章**：v1 用 **Host + GitWorker 两进程**（命名管道 JSON-RPC、Job Object 托管、重启退避+熔断），RemoteSync/LocalScan/StatusCalc 为 Host 内 BackgroundService；**SQLite WAL + 单写者 + Dapper**（锁 ≥3.51.3，DB 放 `%LOCALAPPDATA%`，禁止网络盘）；采集改**分层拉模式**（清单水位 10min → 变化仓 refs 30min → 每日全量对账可续传 P95≤5min；本地 15s 指纹 + 仅变化仓深扫 + FileSystemWatcher）；.NET 10 LTS（.NET 8 已于 2026-11-10 EOL）；WebView2 Evergreen + 离线安装器；DPAPI/Credential Manager + token 读写分离 + 日志脱敏 + `.trash` 可恢复删除。
- **UI/UX**：drawio 主界面几何自相矛盾（卡片区 120px 放不下 4 状态章+分支+2 按钮；右侧 30px 面板放“全部提交历史+CI”）；4,000 组件无搜索/筛选/虚拟滚动/多选，而批量功能已写进需求；无首启向导、任务中心、通知中心、日志诊断、设置页；CI 在 UI 零落点（用户硬性要求）；`*` 标记与搜索冲突；双击打开文件有安全风险。
- **安全**：token 明文 json、可能被拼进 remote URL；无破坏性操作二次确认/审计；无路径穿越与危险扩展名防护。

## 4. drawio 执行合理性审核（结论：不能作为执行依据）

**审核结论**：现图只能算讨论草稿/UI 灵感板，直接交付开发会在 **进程划分、表归属、状态枚举、首启时序、操作闭环** 五处必然返工。

**四条硬理由**

1. **与 docx 结构性矛盾**：进程数 3 vs 4；表数“五表”只定义 3 张、drawio 只画 2 张；状态 5 vs 6；组件聚合键不同。这些“数量”不定，后端架构、DDL、UI 数据绑定都无法冻结。
2. **图内数据链断裂**：聚合节点 `-75` 的唯一入边来自“后端程序开始”（`-76`），**读不到对比结果/表 2**，启动瞬间就会产出空聚合且之后永不再触发；全图没有任何“表/状态 → 前端”的数据边，前端入口 `-55` 是孤立节点——按图实现，看板没有数据源。
3. **核心价值缺失**：docx 的批量 Clone/Checkout/切 Tag/Pull/删除、drawio 文字里的 SYNC/CREATE/dry-run，在图里没有任何节点、没有进度、没有“操作→结果→重扫”回路。图只描述了只读监控。
4. **常驻进程被画成一次性流程**：无结束节点、无节拍（30s/10s/6h 全消失）、无失败/离线/崩溃重启分支；“持续不断”（drawio L8）与“6h 一次 + 120s 超时”（docx L72-73）直接冲突。

**具体缺陷（节选）**

| 缺陷 | 证据（mxCell/dump 行） | 修正方向 |
|---|---|---|
| 聚合依赖边错误 | `-76` 后端开始→聚合（xml L26） | 改为 对比结果/表 3 → 聚合，事件+去抖触发 |
| 表 2 双写 | `-16`（进程 2）与 `-47`（对比结果）都写表 2 | 表 2 只属本地扫描；对比结果写独立 `repo_status`/`component_status` |
| 聚合漏状态 | `-80` 只有 CONFLICT>MISS>BEHIND>AHEAD，无 SYNCED/NEW_BRANCH/else | 补全序判定表 + 默认兜底（见 7.4） |
| `NEW_BRANCH` 判据不成立 | `-34` 第 2 条（drawio L20） | 拆 `NO_UPSTREAM` 三子型；补 DETACHED |
| 首启竞态 | `-5`/`-11` 依赖表 1，但表 1 未就绪时所有本地目录判“否”，无重判回路 | 增加“认证/配置就绪门控”+“表 1 就绪后重判”+ 就绪信号 |
| 空 junction 无 AND/OR 语义 | `-30` 空 ellipse（xml L99-101） | 显式网关 + 双表新鲜度（epoch）判定 |
| 状态栏双定义 | `-93` “最近操作” vs `-99` item7 “进程健康” | 拆两区（状态栏 6 段） |
| 主界面几何不可落地 | `-67` 120×192.5；`-101` 30×181 | 表格默认 + 卡片 ≥320px + 右侧面板 ≥300px |
| 图面卫生 | 后端大框无标题、`elsse` 错字、`构建是否够成功`、Page-2 空白、A4 竖版装不下 2270×1880 内容 | 重排/校对/拆页 |

> 图面勘误：dump 中节点坐标是父容器相对坐标，**“节点越界”的说法不成立**；真实问题是布局重心失衡、回边擦出框顶，以及用边标签表达进程边界。

**建议拆成 6 张图交付**（每张有最小节点清单与可执行验收，详见 `reqs/review/05-drawio-execution.md`）：

| 图 | 名称 | 回答 |
|---|---|---|
| D1 | 系统上下文与进程拓扑 | 几个职责、各自输入/输出表、周期、失败策略、健康心跳 |
| D2 | 启动/停止/异常生命周期时序 | 先认证还是先起服务、首启等什么、崩溃/离线怎么办 |
| D3 | 单仓状态机 + 组件聚合判定表 | 怎么算、怎么合并、是否穷尽互斥、每状态配 git 样例 |
| D4 | 数据流 / ER | 哪张表、谁写谁读、新鲜度、防脏读 |
| D5 | 批量操作闭环时序 | 预检→dry-run→确认→任务→逐仓结果→部分失败→重扫 |
| D6 | UI 线框与数据绑定（含 CI 预留） | 每个区域绑定表/字段/刷新事件；CI 空态 |

拆分规则：D1 的进程/表名 = D4 的表名 = D3/D5 的引用名，三处字符串必须一致；D2/D5 的“就绪/完成”事件必须能在 D1 找到触发源。

## 5. 审核者认为“值得保留”的部分

1. **以组件视角聚合四仓**的产品方向成立，且是本工具不可替代的价值；
2. **远程元数据 + 本地真实 git 双数据源兜底**的方向正确（但要明确“fetch 后的 remote-tracking ref 是关系判定权威，Gitea API 是发现/元数据权威”）；
3. **看板 + 状态色标 + 批量操作**的交互骨架正确；
4. CI 后续接入、界面预留的直觉正确（本次已固化为 10 锚点 + 契约）。

其余具体设计（进程数、表数、状态枚举、色标、drawio 流程）建议**整体废弃重写**，而不是逐条修补。
