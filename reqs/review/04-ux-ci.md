## 总体结论

1. **两套状态色语义互斥且都在生效**：docx L139–143 是"绿=同步/黄=落后/蓝=超前/橙=分叉/红=CI失败或缺失"，drawio L98 是"灰=MISS/黄=冲突/红=超前/绿=同步/其他=滞后"。同一个"门"在两张文档里是三种颜色，"超前"在 docx 是蓝、在 drawio 是红，**而红在 docx 同时表示"CI 失败"**。这不是配色分歧，是**状态模型没有拆成两条正交通道**（仓库生命周期状态 vs CI 状态）。不先修这个，任何界面实现都会在两套色之间反复返工。
2. **主界面示意图（drawio L40–58）无法落地**：组件卡片列表仅 120px 宽（L42），单个组件行 120×22（L43–45），却要求塞下 4 个状态章、分支名、SYNC 与 CREATE 两个按钮（L98–103）。四个文件树各 140×93（L46–49），按钮 55×16（L50–55），而"选中仓库基本信息+所有提交历史+CI 结果"只有 30px 宽（L57 vs L105）——**几何上自相矛盾**，必须拆页。
3. **CI 是本次"不返工"的唯一硬约束，而前端需求给 CI 的界面落点为零**：docx 能力 3（L41–46）要求 CI Building/Pass/Fail 实时联动，数据表也预留了 `ci_status`（L87、L126），但"第三部分 前端 WebView2 详细低阶需求"（L134–150）通篇没有 CI 的任何位置，drawio 只有一句"构建是否成功"塞在 30px 面板里（L57、L105）。**这是返工风险最高项**，必须按下面第 5 节的 10 个锚点 + 契约预留。
4. **1000~4000 组件的规模化交互完全缺失**：两文档都没有搜索、筛选、排序、虚拟滚动、分页、多选批量入口；而 docx L145–148 恰恰要求"批量 Clone / 批量切 Tag / 批量 Pull / 批量删除"。**功能写了，入口没有**。drawio L58 第 8 条"其他功能暂时不表"把这块留成黑洞。
5. **破坏性操作与长任务没有交互规格**：一键整体删除（docx L148）、SYNC 强覆盖（drawio L102）、CREATE 前 dryrun（L103）均无确认界面、无 dryrun 结果表、无任务队列/取消/重试/部分失败展示；drawio 状态栏只显示"最近一次操作的状态"（L53、L107）。四个仓库批量操作**必然出现部分成功**，当前设计无法表达"2 成功 1 冲突 1 跳过"。
6. **v1 建议范围**（可落地 MVP，不含真实 CI API）：1 个 App Shell + 5 个页面（看板 / 组件详情 / 单仓详情 / 任务中心 / 设置）+ 4 个全局层（首启向导、首扫进度、通知抽屉、日志诊断）+ 1 个 CI 占位页与 4 处 CI 徽标/面板锚点 + 13 类必需状态（空/加载/错误/离线/过期/权限/部分失败…）。
7. **"网页级炫酷动效"不可验收**（docx L53）"状态刷新秒级感知"（L56）在当前 30s 轮询 + 10s 计算（L89、L109）下物理不可达（最坏 40s）。已改写为可测指标（第 6 节）。
8. **一句话判断**：保留数据字段，作废主界面布局；先立"双通道状态编码 + 颜色纪律"，再做"看板 ⇄ 详情"两页 IA；CI 只做契约与占位，v1 不接 API 但结构一次到位。

## 统一状态色板（表格：状态 | 颜色/色值 | 展示规则 | 可访问性）

### 2.1 冲突诊断（必须先承认冲突，再谈统一）

| 语义 | docx（L139–143） | drawio（L98） | 冲突性质 | 处置 |
|---|---|---|---|---|
| 同步 SYNCED | 绿 | 绿 | 唯一一致项 | 保留绿，但改为"成功绿"而非荧光绿 |
| 落后 BEHIND | 黄 | "其他颜色为滞后"（**无定义色**） | 颜色缺失，无法验收 | 定琥珀 amber |
| 超前 AHEAD | 蓝 | **红** | 直接矛盾；且红=错误语义，把"正常开发中"画成告警 | 定蓝（采纳 docx） |
| 分叉/冲突 CONFLICT | 橙 | 黄 | 同义异色 + 与"落后黄"撞车（黄既=警告又=错误） | 定紫（避开 amber/红） |
| 缺失 MISS | **红**（且与"CI 失败"合并） | **灰** | 语义冲突 + 数量级冲突：4000 仓库中绝大多数默认未克隆，红=满屏告警 | 定中性灰 + 虚线边 |
| CI 失败 | 红（与 MISS 合并） | 无 | 两套状态混进同一个色槽，是返工根因 | 独立 CI 通道，不进卡片底色 |
| CI 运行中/待定 | 无（仅 L43–45、L87 文字） | 无 | 前端无任何表达 | 新增 CI 通道 |
| NEW_BRANCH 分支缺失 | 无 | 有状态、**无颜色**（L20） | 状态无视觉 | 新增青色 |
| 数据过期/未知 | 无 | 无 | 无法表达"30s 轮询失败/离线" | 新增斜纹灰 |

> 关键判断：**禁止把 CI 状态编码进仓库状态色域**。docx L143 "红色：CI失败 / 仓库缺失异常"用斜杠把两条正交维度合并，是本次设计最需要推翻的一句。

### 2.2 双通道编码原则

- **通道 A（仓库生命周期）**：色相 + 形状（实底 chip）+ 图标 + 文案，落在 4 个子仓 chip（D/I/M/S）与组件聚合徽标上。
- **通道 B（CI 状态）**：**不得**染卡片底色/子仓 chip；只允许出现在固定位置的 CI 徽标（12px 圆点 + 图标 + 文字），形状与通道 A 不同（描边 pill / 圆形）。
- **卡片本体颜色纪律**：卡片底色 **中性**；聚合异常只用「左侧 4px 状态轨道 + 右上角聚合徽标」，**不再整卡饱和色**（推翻 drawio L99 与 docx L137 的"整卡变色"读法）。这样一张卡最多 4 个小色块 + 1 个 CI 点，视觉噪声可控。
- **永不单靠颜色**：每个状态必须同时具备 图标 + 文案（或 `aria-label`），满足色盲与灰度打印。

### 2.4 通道 B · CI 状态色板（独立、不与 A 撞色）

| 状态 | 颜色/色值 | 展示规则 | 可访问性 |
|---|---|---|---|
| **CI PASS** | 浅 `#15803D`；深 `#4ADE80` | 12px 实心圆 + ✓ + 文案「CI 通过」；仅在 CI 徽标/CI 列内 | 与 A 的 SYNCED 同为绿，但**形状不同**（圆点 vs chip 实底）+ 位置固定 + 必有文字 |
| **CI FAIL** | 浅 `#C81E1E`；深 `#F87171` | 12px 圆 + ✕ + 2px 描边 pill + 「CI 失败」+ 失败阶段名；可带轻微 1 次脉冲 | 红只在 CI 通道；✕ 与 ✓ 形状互补；禁止仅红块 |
| **CI RUNNING** | 浅 `#1D4ED8`；深 `#60A5FA` | 环形 spinner 或半环 ◐ + 「运行中」；`prefers-reduced-motion` 下静态 ◐ | 动效不作为唯一信号；spinner 在 reduced-motion 停止 |
| **CI QUEUED** | 浅 `#6B7280`；深 `#9CA3AF` | 虚线空心圆 + ⏱ + 「排队中」 | 空心/实心/描边三态可辨 |
| **CI NONE（无流水线）** | 浅 `#9CA3AF`；深 `#6B7280` | 空心 ∅ + 「无 CI」；不报警、不占优先级 | 中性灰；与 MISSING 靠位置+形状区分 |
| **CI UNKNOWN（无权限/超时）** | 浅 `#6B7280` + 斜纹 | ? + 「CI 未知」；悬停显示原因（Token 失效/429/超时） | 斜纹+问号；不得当作失败 |

**颜色纪律（写进验收）**：① 一个可视区域内，红只允许出现在 CI FAIL 与破坏性确认按钮；② 分叉用紫、缺失用灰、超前用蓝，任何实现不得回退到 drawio L98 的红=超前/黄=冲突；③ 状态色只能来自本节 token（CSS 变量 `--st-*`），硬编码 hex 视为不通过。

### 2.5 主题与可访问性基线

- token 化：`--st-synced-fg/bg/bd`、`--st-behind-*`、`--st-ahead-*`、`--st-diverged-*`、`--st-missing-*`、`--st-newbranch-*`、`--ci-pass/fail/running/queued/none/unknown`；浅/深两套只换值不换名。
- 深色主题：画布 `#14161A`，卡片 `#1C1F26`，分隔线 `#2A2E36`，正文 `#E6E8EB`；**禁止纯黑 #000 / 纯白 #FFF**；深色下状态色统一提亮 8–12%（上表已给深色值）。
- 对比度：正文 ≥4.5:1；非文本（边框/图标/焦点环）≥3:1；状态 chip 内文字与底色 ≥4.5:1。
- 焦点：2px `#2563EB` 环 + 2px offset，任何状态色背景上均可见；`forced-colors: active` 下不丢失状态（用 border-style 区分）。
- 尺寸：点击目标 ≥24×24 CSS px（WCAG 2.2 AA），主要按钮高 ≥32px——drawio 的 55×16 按钮（L50–55）**不合规**，需放大或改图标按钮。
- 缩放：200% 缩放下看板与详情不横向溢出（布局用 minmax + 容器查询）。
- 色彩验证：交付前跑 deuteranopia/protanopia 模拟 + axe 对比度扫描；`prefers-color-scheme`、`prefers-reduced-motion`、`prefers-contrast` 三开关必须被遵守。

### 3.2 v1 导航模型

- 全局导航只到 P1–P8 七个页面；从看板卡片 → 组件详情（P2）→ 子仓（P3）→ CI Tab（P3 内预留）为**单一纵深路径**，避免 drawio 单页塞全部。
- 看板与详情之间保留 `Esc`/面包屑返回；批量操作不离开看板（任务抽屉覆盖层进行）。
- 首启向导、首扫进度、故障页属于 L0，**不进入**全局导航。

## CI 预留契约与"不返工"验收标准

### 5.1 数据契约（前端只依赖这个形状，v1 由 Mock 提供）

```ts
// 单仓最新 CI 状态（列表/徽标用）
type CiState = 'PASS' | 'FAIL' | 'RUNNING' | 'QUEUED' | 'NONE' | 'UNKNOWN';

interface CiLatest {
  repoId: string;            // 组件前缀+仓库类型派生
  componentPrefix: string;
  repoType: 'design' | 'impl' | 'mil' | 'sil';
  branch: string;
  commitHash: string;        // ★ 必须与"该提交"绑定，而非"仓库最新"
  state: CiState;
  pipelineId?: string;       // 外部系统 id，v1 = mock-*
  buildNumber?: number;
  failedStage?: string;      // 如 'unit-test' / 'compile'
  startedAt?: string;        // ISO8601 UTC
  finishedAt?: string;
  durationMs?: number;
  url?: string;              // 打开外部流水线
  provider: string;          // 'mock' | 'gitea-actions' | ...
  fetchedAt: string;         // 数据新鲜度，UI 必须展示
}

interface CiEvent {          // 事件通道预留（SignalR/SSE 均可，属其他评审）
  type: 'CI_UPDATED';
  payload: CiLatest;
}

// 组件级聚合（与仓库聚合严格并列，不混合）
interface ComponentCiAggregate {
  componentPrefix: string;
  byState: Record<CiState, number>;   // 4 仓计数
  worstState: CiState;                // 优先级 FAIL > RUNNING > QUEUED > UNKNOWN > PASS > NONE
  lastFailed?: Pick<CiLatest, 'repoType' | 'buildNumber' | 'failedStage' | 'url'>;
  dataFreshAt: string;
}

// v1 唯一实现
interface ICiProvider {
  getLatest(componentPrefix: string): Promise<CiLatest[]>;
  getAggregate(componentPrefix: string): Promise<ComponentCiAggregate>;
  subscribe(cb: (e: CiEvent) => void): () => void;   // v1 空实现，返回 noop
}
```
约束：① CI 状态**必须挂在 commitHash 上**（docx L42 "绑定每一次 Commit 的 CI 结果"），不能只挂仓库；② 未提交本地改动（`*`）不应显示 CI 徽标，而是显示"未推送/无构建"中性态；③ 空值一律 `NONE`/`UNKNOWN`，禁止用红表达"没数据"。

### 5.2 存储/配置预留（仅 UI 依赖面，选型归其他评审）
- 表/字段：`ci_pipeline(repo_id, commit_hash, branch, state, build_number, failed_stage, started_at, finished_at, url, provider, fetched_at)`；`git_local_cache.ci_status` 保留但**仅作缓存副本**，UI 以 `ci_latest` 视图为准（避免 docx L87 的 `ci_status` 被误读为"仓库状态"）。
- 配置：`ci.enabled=false`、`ci.baseUrl=''`、`ci.token=''`、`ci.pollIntervalSec=60`（v1 全部只读/禁用）。
- 事件：`CI_UPDATED`、`CI_QUEUE_CHANGED` 两个消息类型注册在 IPC 契约里（v1 不发送）。

### 5.3 占位组件规范（禁止"TODO 白块"）
统一 `<CiSlot variant="badge|strip|tab|queue|facet|notification">`：有固定尺寸、有 `data-state`、有骨架（加载）、有空态（"即将上线"）、有 tooltip（"CI 集成将在后续版本开放"）、`aria-label` 完整、可被开关 `ci.enabled` 一键点亮。**所有占位必须能被 feature flag 打开后显示 Mock 数据**，以证明结构可承载。

### 5.4 "不返工"验收标准（可检查、可自动化）
1. 上述 CI-1…CI-10 共 10 个位置**全部存在**，路由/锚点/组件名固定；用 UI 快照测试断言存在性。
2. 组件卡片有且仅有 1 个 CI 槽位（CI-2），在 1280/1440/1920 三档下不换行、不遮挡；卡片高度变化 ≤0px（槽位定高）。
3. 卡片底色 = 中性 token；聚合状态只由 4 仓状态决定；**CI 状态变更不改变卡片底色**（用单测/视觉回归注入 CI FAIL 断言底色不变）。
4. 任意 CI 状态组合下，看板仍满足颜色纪律（红仅出现于 CI FAIL 与危险按钮）。
5. 单仓详情必有第 4 个 Tab「CI」，其空态文案与骨架可渲染；Tab 顺序不进 CI 时也不重排。
6. `ICiProvider` 的 Mock 实现只需改配置 `ci.enabled=true` 即可让 CI-2/3/4/5/7 显示数据，**无需改组件结构**（集成测试覆盖）。
7. 事件契约 `CI_UPDATED` 在 IPC 层有类型定义与处理分支（v1 收到即更新对应徽标，可 Mock 触发验证）。
8. CI 聚合优先序、未知/无数据语义、数据新鲜度展示在契约文档中冻结；UI 不自行发明状态。
9. 在 CI 未接入时，任何页面**不得出现裸露的"TODO/敬请期待"文本块**，必须走统一 `CiSlot` 空态。
10. 视觉回归基线包含：6 个仓库状态 × 6 个 CI 状态的关键组合（≥12 张快照），未来接入真实 CI 只需替换数据不改样式。

### 6.1 4000 卡片 / WebView2 性能预算（可量化）

| 指标 | 预算 | 测量方式 |
|---|---|---|
| 首屏可交互（数据就绪后） | ≤1.5s | Performance 时间线 |

| 状态刷新重绘 | 只更新变化的行/卡（keyed diff），单批 ≤16ms，不得整表重渲染 | Profiler 火焰图 |
