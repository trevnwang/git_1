## 总体结论（drawio 是否可作为执行依据）

**结论：不能。该 drawio 目前不是"可执行方案"，只能作为需求讨论草稿/UI 灵感板；若直接交付开发，会在进程划分、表归属、状态枚举、首启时序、操作闭环五处必然返工。**

四条硬理由：

1. **与 docx 存在结构性矛盾，且矛盾点在"数量"上**：进程数 3 vs 4（docx L61/L79/L95 ↔ dump L4-6、L27、xml L76）；表数 docx 声明"五表"只定义 3 张（docx L114-132）↔ drawio 只画 2 张（dump L8/L14/L26）。这两个数字没定，后端架构、DB schema、UI 数据绑定全部无法冻结。
2. **图内数据链是断的**：对比结果（dump L18-25）→ 聚合（L27-29）→ UI 之间没有数据边；聚合节点唯一的入边来自"后端程序开始"（`-76`，xml L26），读不到"对比结果/表2"；全图没有任何"表/状态 → 前端程序"的边（前端唯一入口 `-55` 是孤立开始节点，xml L183）。按图实现，看板拿不到数据。
3. **工具的核心价值（组件级批量操作）在图里不存在**：docx 的 Clone / Checkout / 切 Tag / Pull / 删除（L32、L145-148）与 SYNC / CREATE（dump L58 3.5/3.6）在流程图里没有任何节点、没有 dryrun、没有进度、没有"操作→结果→重扫"回路。图目前只描述了"只读监控"。
4. **常驻进程被画成一次性流程图**：无结束节点、无定时节拍、无失败分支、无崩溃重启、无离线分支（docx L157 明确要求自动重启；图里没有）。"持续不断"（dump L8）与"6h 一次 + 120s 超时"（docx L72-73）直接冲突。

**可执行性评级（按图能否直接驱动实现/测试）**

| 维度 | 结论 | 说明 |
|---|---|---|
| 进程模型 | 不可执行 | 4 进程无定义、边界用边标签表达、聚合依赖错 |
| 数据流 | 不可执行 | 2 表 vs 3/5 表、双写、无 UI 消费边、无新鲜度 |
| 启动/时序 | 不可执行 | 首启竞态、认证位置错、无 gate/失败分支 |
| 状态闭环 | 不可执行 | 6 态 vs 5 态、聚合漏 2 态、无操作回流 |
| 图面可维护 | 勉强可读 | 布局失衡、空节点/悬挂边、错别字、空页 |
| 作为交付物 | 不合格 | 流程图+数据流+状态表+UI 线框混在一页 |

**要变成可执行依据，至少需满足**：(a) 进程数与表清单用户拍板；(b) 补 进程3→进程4 的数据依赖与"双表新鲜"屏障；(c) 状态判定与聚合写成穷尽互斥判定表（含兜底）；(d) 补首启/认证/失败/离线分支；(e) 补批量操作闭环；并拆成 5-6 张图（见文末"图集拆分"）。满足前不进入编码。

## 流程/时序问题（按严重级）

### P0 级（阻断：按图无法实现）

**A. 进程模型不自洽（P0-01）**
docx 明确 3 进程且聚合是进程3 的规则；drawio 出现"进程4 聚合"。但 drawio 自己的"进程"也不是泳道，而是三条边上的标签：`-28`=进程1（xml L13）、`-29`=进程2（L21）、`-77`=进程4（L29）、`-32`=进程3（L94）。节点归属只能靠边猜：例如"记录对比结果到本地表2"（`-47`）位于从遍历（`-5`）出发的循环上，到底属于进程2 还是进程3，图上无法判定。**后果**：进程清单、线程/并发模型、失败域、监控项（状态栏 item7）全部无法落。

**B. 聚合依赖边方向与语义错误（P0-02）**
`-76: 后端程序开始 → 聚合`（xml L26）。聚合的输入应是"对比结果/表2/表3"，图里却把它挂到启动节点上：若实现，聚合在启动瞬间执行一次，此时表1 可能为空（4000 仓同步未开始）、表2 未扫，输出全 MISS 或空；且之后无任何边再触发聚合 → 组件状态永久陈旧。这是"控制流边冒充数据流边"的典型错误。

**C. 状态结果到 UI 的数据流断裂（P0-03）**
全图没有一条边从 `-34 对比结果`/`-47`/`-75 聚合`/任何"表"指向"前端程序"。前端唯一入口 `-55 前端程序开始` 是孤立节点（xml L183），与 `-56/-58/-99` 串成一条与后端完全无关的链；`-51`（认证→后端容器 `-44`）与 `-54`（认证→前端容器 `-52`，xml L171/L177）是**指向容器而非节点**的边，drawio 语义上只是"落在框上的箭头"，无法对应具体步骤。**后果**：看板（docx 能力2 的核心交付）没有数据来源；"秒级感知"（L56）无实现路径。

**D. 表2 双写、表归属冲突（P0-04）**
`-16`（进程2）写表2（L14），`-47`（对比结果）又"记录到本地表2"（L26）。docx 中表2 唯一属于进程2（L93），对比结果属于表3（L112）。若照图实现：同一张表两个写者、字段语义不同、无锁无幂等键 → 状态错乱；若把 `-47` 的表2理解为表3，则全图表号与 docx 对不上，schema 仍无法定稿。

**E. 聚合漏掉关键状态，"健康"不可达（P0-05）**
聚合规则只有 CONFLICT/MISS/BEHIND/AHEAD 四条 `else if`（L30-33），没有 `SYNCED`、没有 `NEW_BRANCH`、没有 `else`。最常见的"四仓全 SYNCED"没有任何规则命中 → `component_full_status` 为空/未定义 → 看板无法显示"绿色正常"，docx L139 的绿色语义在图上不可达。这是状态闭环的硬断点。

**F. 状态机枚举不成立（P0-06）**
`NEW_BRANCH`（L20）定义为"本地仓库存在，但本地仓库的当前分支不存在"——git 语义上本地当前分支必然存在于本地 refs；该状态实际想表达"远程有该分支、本地未跟踪/fetch 未到"，命名与判据不符，实现者会写出三种不同判定。同时 6 态判定是"列表"不是"判定树"：3/3.1/3.2/4/5 之间缺少互斥性与执行顺序定义（L21-25），且完全缺 DETACHED HEAD（批量切 Tag 必现，docx L146）、"远程仓库已删除但本地仍在"的孤儿态。

**G. 组件聚合键错误（P0-07）**
`-78` 示例把 `CF325F_ChanganSigProcgBascFct_Design/Impl/MIL/SIL` 聚成组件 `CF325F`（dump L28 长文本），而 docx L14 定义组件=`CF123A_ShortName`（即前缀+短名），仓库=组件+后缀。按图的示例，所有同前缀不同短名的组件会被错误合并；而"相同前缀"到底怎么切（按最后一个下划线？按已知四后缀？）全图没写。docx L49 又说"命名全局唯一，无需校验前缀合法性"，这条规则与"按前缀聚合"的切分算法不兼容，必须给出可执行的切分规则。

**H. 组件级批量操作闭环缺失（P0-08）**
图中没有：批量 Clone（docx L145）、批量 Checkout、批量切 Tag（L146）、批量 Pull、组件整体删除（L148）、卡片 SYNC/CREATE（dump L58 3.5/3.6）。也没有 SYNC 的"本地有变更/超前→强制覆盖确认"分支、CREATE 的 dryrun 判定（3.6 明确 dryrun）、操作进度、部分失败、操作后重扫触发。**后果**：产品定位"屏蔽底层仓库、以组件视角操作"在图里没有一条可执行路径；无法据此写端到端测试。

**I. 首启时序与配置竞态缺失（P0-09）**
`-5` 依赖"本地指定文件夹"、`-3` 依赖 Gitea 组织/URL/token，但这些配置只在 UI 菜单栏产生（dump L58 item1），后端却"开始→立即三路并发"（`-4/-22/-76`），无"配置就绪/已登录"门控。更严重的是 `-11` 判断"是否 gitea 该组织同名仓库"依赖表1，而表1 要等进程1 首次全量同步完成；首启时表1 为空 → 所有本地文件夹被判"否"→跳过 → 本地组件在首启阶段全部不可见，且图里**没有"表1 就绪后重新判定"的回路**。前端 `-56` 只等"进程2 遍历进度"，而遍历完成 ≠ 组件列表可用（列表还需表1+聚合），没有"数据就绪"信号；遍历也无 total 计数（非递归、边数边查），进度条无法计算。

**J. CI 数据流矛盾且 UI 无预留（P0-10）**
drawio 把 build result 放进表1（`-3`，L8），docx 把它放进表2 `ci_status`（L87）并由进程2 每 30s 取（L82）。docx L41-46 要求"自动绑定每一次 Commit 对应的 CI 结果（Building/Pass/Fail）"，是 (repo, commit)→状态 的二维关系，两张图的表结构都装不下（表1 无 commit 维度；表2 单值 ci_status 丢历史）。同时 docx L46 "实时预警"、L56 "秒级感知"与进程1 的 6h 周期（L72）互斥；drawio 图内完全没有 CI 状态节点、CI 聚合规则、CI 颜色、UI CI 区域——而"CI 预留区域"是用户硬性要求。**后果**：CI 需求既无数据模型也无界面挂载点。

### P1 级（高危：语义可解释但实现必踩坑）

**P1-01 进程1 周期与容量不自洽。** "持续不断"（L8）vs 6h/120s/重试2（L72-74）。按 4000+ 仓（docx L13/L63）× 每仓至少 3-4 次 API（repo/branches paged/tags paged/latest commit）≈ 1.2-1.6 万请求，120s 需稳定 100+ req/s，Gitea 单实例+网络延迟下不现实；首启全量同步必然超时进入无限重试。图里也没有分页、并发度、失败仓重试队列。

**P1-02 循环没有节拍、没有终止判定、没有屏障。** 遍历链 `-5→-11→(-13→-5)` 与对比链 `-16→-30→-25→-34→-47→-5`（xml L43/L66-72）都是"边回环"，无 sleep/interval 节点、无"遍历完成"判定、无"全部扫描完成后才聚合"的 join。按图实现 = 每发现一个文件夹就做一次对比并回写，4000 次比较；同时"对比结果"是全局表 `-34`，逐文件夹写入会产生中间态。docx 的 30s/10s 周期（L89/L109）在图里完全消失。

**P1-03 进程2 语义被偷换。** drawio 进程2 = 一次性全盘遍历（L9），docx 进程2 = 30s 增量轮询（L89-91）；首启"需要耗时"的遍历（L38）与常驻轮询被合并成同一标签，导致状态栏无法区分"首启扫描中"与"常驻监控正常"。

**P1-04 认证位置与双入口。** 流程 `开始 -45 → 认证 -50 → {后端 -44, 前端 -52}`（dump L34-35、L76-77）意味着认证先于程序；docx 的认证在 UI 菜单栏内（L58 item1），且 token 是进程1 的前置条件（远程 API）。图里既无"未登录/凭据过期"分支，也无"前端配置写 json → 后端读取"的交接节点（`-99` item1 提到 json，但无节点）。

**P1-05 无结束/无失败/无自恢复/无离线。** 常驻进程图必须区分"进程退出/重启"与"业务步骤"，图里只有一个"后端程序开始"，没有结束/异常出口；没有 401/403/429/超时/网络断开/git 命令失败/仓库损坏/路径不存在/磁盘满 分支；没有 supervisor/watchdog（docx L157 "任意进程崩溃自动重启"）、没有离线/内网降级（汽车研发内网常见，图里无论证）。`-13 跳过` 是一条死胡同式节点（只回 `-5`，无"遍历完成"出口）。

**P1-06 空 junction 与快照语义缺失。** `-30` 是一个 30×30 的**空 ellipse**（dump L17、xml L99-101），被当作 `-3`（远程同步）与 `-16`（本地扫描）的汇合点、再流向对比。它既不是 junction 也不是 AND/OR 网关：`-26` 与 `-27` 两条边谁先到？需要两表都新才比较，还是任一更新就比？没有语义。且两表没有 epoch/updated_at/compare_generation 列（docx 表2 有 scan_time，表1 有 update_time，但图未使用），比较可能读到"半新快照"（进程1 正在写表1、进程2 只扫到一半）→ 状态抖动、误报 BEHIND/CONFLICT。

**P1-07 CI 新鲜度矛盾（与 P0-10 联动）。** 若 CI 结果只随进程1 每 6h 刷新，则"实时预警/秒级感知"（docx L46/L56）不成立；docx 本来让进程2 30s 取 CI（L82/L87），drawio 把它移到进程1，等于把 CI 时效从 30s 降到 6h。UI 状态栏也没有"CI 数据时间"或"远程数据时间"的新鲜度展示。

**P1-08 本地目录布局契约缺失。** `-5` 只取"直接子文件夹（非递归）"，隐含 `<root>/<repo>` 平铺；但组件四仓是否可能嵌套为 `<root>/<component>/<repo>`？若嵌套，非递归遍历永远找不到仓库；若平铺 4 个同级目录，则"组件"只能靠名字聚合（回到 P0-07）。该布局契约是"能否在本地找出组件"的充要条件，图里没有。

**P1-09 "临时库"与持久化/膨胀矛盾。** `-3` 说表1 是"本地临时远程数据库"（L8）、`-16` 说表2 是"临时本地数据库"（L14），docx 却要求持久化多表、支持千级仓库元数据（L55/L25）；而表2 记录"所有 commit"（L14）在 4000 仓/多分支下会无界膨胀。没有清理/保留策略、没有"临时"与"缓存"的边界定义。

**P1-10 聚合输出表未命名、无字段。** `-78`"列新的数据表"（L28）没有表名、没有字段清单；docx 表3 字段为 repo_status / is_error / error_msg / component_full_status（L129-132），其中前 3 个是"单仓级"、最后 1 个是"组件级"，**同一张表混两个粒度**，本身就缺主键（repo 还是 component？）。加上"五表"缺 2 张（L114），schema 无法生成 DDL。
