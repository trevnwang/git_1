# 需求评审报告 01 — 需求质量（对抗式评审 / Requirements Critic）

- 评审对象：`reqs/MBD组件全生命周期Git工具.docx`（转写 `_tools/docx_dump.txt`，简称 **docx L**）、`reqs/software_workflow.drawio`（转写 `_tools/drawio_dump.txt`，简称 **drawio L**）

## 总体结论

草案只能算一份**带实现设想的功能愿望清单**，不是可开发、可验收的 SRS：核心业务实体「组件」的命名与绑定规则自相矛盾（`CF123A_ShortName` vs 聚合成 `CF325F`），状态模型、颜色语义、进程数量、表数量在两份文档间各说一套，"极简五表"只定义 3 张且 3 张表没有任何主键/外键/必要字段，全文没有一条可执行验收条件，HLR 承诺的版本/基线/CI 管理在 LLR 中无对应设计。唯一可直接保留的是三个方向性判断：**以组件视角聚合四仓**、**远程元数据 + 本地 git 双数据源兜底**、**看板式状态可视化**；但这些必须按本报告的建议条款重写为带 ID、带枚举、带 AC 的 SRS 才能进入开发。建议整体否决 v0.1，按「建议的新需求文档结构」重建 SRS v0.2 后再评审一次。

## 建议的新需求文档结构（章节级，可直接采用）

> 采用"文档控制 + 范围 + 领域模型 + 功能 + 非功能 + 验收"结构；每条需求使用统一模板字段：`ID | 标题 | 优先级(MoSCoW) | 来源(HLR/UC/决策) | 描述 | 前置条件 | 主流程 | 异常分支 | 数据变更 | 验收标准(AC, Given/When/Then) | 状态(active/deferred/TBD)`。

1. **文档控制**：文档 ID、版本、生效日期、作者/评审人/审批人、变更记录、术语表引用、评审结论归档。
2. **背景与目标**：痛点（4000+ 仓库 vs 组件视角）、产品定位、可度量的成功标准（如状态新鲜度、批量操作耗时、误操作率）。
3. **范围与优先级**：v1 In-Scope / Out-of-Scope 清单、MoSCoW、里程碑、角色定义、假设/依赖/风险、与 v2 的边界（CI、基线）。
4. **术语与领域模型**：Component / Repo / 生命周期类型 / 状态枚举 / 颜色映射 / tag_consistency / 刷新语义；命名语法与归一化规则；未归类仓库处理；ER 图。
5. **用户场景（UC）**：首次接入、日常看板巡检、批量 Clone、批量切 Tag、单仓提交推送、删除清理、断网/降级、误操作恢复——每场景 1 个 UC + AC。
6. **功能需求（FR）**：按能力分组：组件聚合（CMP）、状态感知（STA）、Git 操作（OP）、安全与破坏性操作（SAFE）、认证配置（AUTH）、同步（SYNC）、检测兜底（DET）、UI（UI）；每条带 AC。
7. **状态与聚合规则**：单仓 7 状态定义表、组件聚合优先级、stale/UNKNOWN 规则、tag_consistency、刷新触发。
8. **数据与接口**：ER + 字段/枚举/主外键、Gitea API 契约（分页/限流/错误码）、CI 接口（v1 关闭，仅定义占位）、本地 git 调用契约、错误码表。
9. **UI 交互与视觉**：页面清单（看板/设置/仓库详情/日志）、状态→图标+文字+颜色映射表、空/错/加载/首次态、进度与取消、颜色令牌由 UI 设计系统给出（本报告只锁定语义）。
10. **非功能需求（NFR）**：性能（量化+测试机+数据集）、容量、可靠性/离线降级、安全（凭据/审计/权限）、日志与诊断、部署/升级/卸载、兼容性、数据生命周期。
11. **验收与测试**：AC 编号与追溯矩阵（HLR→FR→AC）、验收数据集与脚本、验收环境、门禁标准（P0 未闭环不得进入开发）。
12. **开放问题与决策记录**：ADR 列表（组件身份、状态集合、CI 范围、删除作用域、凭据方案、技术栈），每条含选项/结论/日期/决策人。
13. **附录**：流程图（drawio 作为示意图）、原型截图、变更记录、外部参考链接。
